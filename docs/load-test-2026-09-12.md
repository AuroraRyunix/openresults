# Load test, 2026-09-12: OpenResults on one pinned CPU core

Local load test against a production-mode OpenResults instance, deliberately
pinned to a single CPU core so a measurement on this desktop says something
about the 2 vCPU production box. Everything below ran on:

- Intel Core i7-10700 (8 cores / 16 threads @ 2.9 GHz), Windows 11 IoT
  Enterprise LTSC 2024
- Erlang/OTP 29 (erts-17.0.5), Elixir 1.20.3, Phoenix 1.8.13, Bandit 1.12.5,
  Finch 0.23.0
- Repo at `9e930cd` (main, clean) plus two already-modified fixture files
  that predate this test and were left untouched

No application code was changed. The only new file is this one.

## 1. How the server was started

Production mode, not a compiled release, because that is how the real
deployment runs it: `docs/deployment.md` describes the unit compiling the
source on the target and starting it with `MIX_ENV=prod` directly (no `mix
release` anywhere in that document). Matching that meant running `mix
phx.server` under `MIX_ENV=prod` rather than building a release, and doing
the two things a release would otherwise do automatically:

```powershell
$env:MIX_ENV = "prod"
$env:DATABASE_PATH = "...\scratchpad\loadtest\openresults_loadtest.db"
$env:SECRET_KEY_BASE = "<mix phx.gen.secret output>"
$env:PHX_HOST = "localhost"
$env:PORT = "4004"
$env:PHX_SERVER = "true"
$env:OPENRESULTS_INGEST_TOKEN = "<random 40-hex token>"
$env:POOL_SIZE = "5"        # the production default, left alone deliberately

mix deps.get
mix compile
mix ecto.create
mix ecto.migrate
mix assets.deploy          # digests + gzips priv/static, same as prod
```

`mix assets.deploy` matters for realism: `Plug.Static`'s `gzip:` option in
`lib/openresults_web/endpoint.ex` is keyed off `code_reloading?`, which is
`false` outside dev regardless of how the server is started - so gzip and the
cache manifest behave the same here as under a real release.

Then, in production mode, two configurations of the server were run and
compared (see §5):

```powershell
# "matched": one BEAM scheduler for the one pinned core
elixir --erl "+S 1:1" -S mix phx.server

# "mismatched": BEAM's own default (one scheduler per logical CPU), pinned anyway
mix phx.server
```

Both were started detached (`Start-Process cmd.exe /c ...` redirecting
stdout/stderr to files under `scratchpad\loadtest\results\`), then pinned:

```powershell
$serverPid = (Get-NetTCPConnection -LocalPort 4004 -State Listen).OwningProcess
(Get-Process -Id $serverPid).ProcessorAffinity = [IntPtr]1   # core 0 only
```

Verified both ways: `Get-Process -Id $serverPid | select ProcessorAffinity`
read back `1` (binary `...0001`) immediately after, and `(Get-Process
-Id $serverPid).Threads.Count` was checked against the scheduler count below.

**Schedulers actually started, on this 16-logical-CPU box:**

| Config | `+S` flag | OS threads (`Get-Process ... Threads.Count`) | Erlang scheduler count |
|---|---|---|---|
| default (`mix phx.server`) | none | 84 | 16 online (one per logical CPU - confirmed separately via `:erlang.system_info(:schedulers)` from a throwaway `elixir -e`) |
| matched (`+S 1:1`) | `+S 1:1` | 23-24 | 1 online |

## 2. Loading a realistic tournament

Generated, not hand-written, via a small Python script
(`scripts/generate_snapshot.py`, scratchpad only) producing a 128-player,
9-round Swiss-shaped snapshot: round-robin (circle-method) pairings so every
round is a full bracket, results drawn from the app's own result-token
vocabulary (`1-0`, `0-1`, `1/2-1/2`, `1-0FF`, `0-1FF`, occasional `null`), and
a `standings` block ranked by points with a placeholder tiebreak column - it
does not reproduce the `working` per-round tiebreak breakdown the real
OpenPairings builder emits (that field is optional and every accessor in
`OpenResultsWeb.Tournament` tolerates its absence), so the payload is smaller
than an equivalent real one (~74 KB vs. the ~580 KB the `Revalidate` module's
own docs cite for a 300-player/11-round event) and the rendered pages are
correspondingly a bit lighter than a maximally-detailed real tournament would
produce. It is otherwise the real shape: same player/round/board/standings
structure the renderer actually walks.

Loaded through the real, running server's own ingest endpoint - not by
touching SQLite directly:

```bash
curl -X POST http://localhost:4004/api/snapshots \
  -H "Authorization: Bearer $OPENRESULTS_INGEST_TOKEN" \
  -H "Content-Type: application/json" \
  --data @snapshot_loadtest.json
# => {"status":"ok","slug":"loadtest-open-2026","received_at":"..."}
```

Confirmed all four page types render for real content before load-testing:

| Page | Status | Size |
|---|---|---|
| `/t/loadtest-open-2026` (standings) | 200 | 114 KB |
| `/t/loadtest-open-2026/round/5` | 200 | 71 KB |
| `/t/loadtest-open-2026/crosstable` | 200 | 463 KB (confirmed the heaviest page, as `Revalidate`'s docs say) |
| `/t/loadtest-open-2026/player/1` | 200 | 33 KB |

`ETag`/`If-None-Match` confirmed working before load-testing too: a second
request carrying the first response's `ETag` got back a bare `304` with no
body.

## 3. The load generator

`scripts/loadgen.exs` (scratchpad only, not part of the repo), run as:

```powershell
mix run --no-start scripts\loadgen.exs -- `
  --concurrency 200 --duration 8 --mode fresh --label c200 --out results.jsonl
```

`--no-start` loads the project's compiled code - so `Finch`, `Req` and
`Jason` (all already dependencies; `Req`/`Finch` because
`OpenResults.FideLookup` uses them) are on the path - without booting
`OpenResults.Application`, which would otherwise try to bind port 4004 a
second time and collide with the server under test.

It simulates a hall of phones hitting four page types in realistic
proportion - standings 35%, a round 25%, the cross-table 10%, a player card
30% (round and player numbers drawn uniformly across all 9 rounds / 128
players) - with `--concurrency` workers each running a closed loop (issue
request, wait, issue the next) for `--duration` seconds. `--mode conditional`
switches every worker to a fixed URL per page type with a pre-fetched
`If-None-Match`, simulating a phone re-polling a page it already has.

Two bugs surfaced and were fixed while getting this working, both worth
recording since they'd trip up a repeat of this test:

- **IPv6-only loopback on this box.** `config/runtime.exs` binds
  `ip: {0,0,0,0,0,0,0,0}` (the IPv6 wildcard) in prod. On this Windows
  machine that does **not** dual-stack to IPv4: a raw `:gen_tcp.connect` to
  `127.0.0.1` got `:econnrefused` while the identical connect to `::1`
  succeeded. `curl.exe` never showed this because it happens to resolve
  `localhost` to `::1` first here. Fix (client-side only): connect to `::1`
  explicitly, with `conn_opts: [transport_opts: [inet6: true]]` on the Finch
  pool (Mint otherwise treats the bare `"::1"` string as a hostname to
  resolve, not a literal address, and fails with `:nxdomain`), and an
  explicit `"host"` header override (`"localhost:4004"`) since Mint sends the
  unbracketed literal as the wire `Host:` header, which Bandit rejects with a
  bare `400`.
- **`mix run` scripts that never exit.** Without an explicit `System.halt(0)`
  at the end, each load-generator invocation left an orphan BEAM process
  behind (visible as extra `erl.exe` processes), quietly adding unrelated
  scheduler load to every later step. Fixed by halting explicitly once the
  summary is written.

One more thing observed and worth flagging rather than hiding: partway
through setup, unrelated `mix test` / `mix precommit` processes (not started
by this test) were found running against the same checkout and were cleared
before the measured ramp began, since they'd otherwise compete for the same
pinned core. None reappeared during the actual measured ramp below.

## 4. Results: the concurrency ramp (matched config: `+S 1:1`, pinned to core 0)

`--mode fresh`, 8 seconds per step, warmed once at the start of the ramp by
requesting every one of the 139 distinct pages once (so steady-state
page-cache-hit behaviour is what's being measured, not first-render cost -
see §6 for that cost separately):

| Concurrency | RPS | Errors | Median | p95 | p99 | Max | Server CPU (of 1 core) | Server RSS |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 2446 | 0 / 19572 (0%) | 3.5 ms | 6.3 ms | 19.1 ms | 166 ms | 90% | 98 MB |
| 25 | 2304 | 0 / 18434 (0%) | 9.2 ms | 21.0 ms | 36.9 ms | 438 ms | 92% | 100 MB |
| 50 | 2130 | 0 / 17043 (0%) | 18.8 ms | 40.2 ms | 81.6 ms | 588 ms | 82% | 101 MB |
| 100 | 2142 | 0 / 17136 (0%) | 38.9 ms | 75.2 ms | 213 ms | 557 ms | 93% | 102 MB |
| 200 | 1788 | 0 / 14301 (0%) | 81.8 ms | 139 ms | **1219 ms** | 1713 ms | 92% | 104 MB |
| **400** | **906** | **2846 / 7245 (39.3%)** | 183 ms | 1988 ms | 2581 ms | 3363 ms | 96% | 360 MB |
| 800 | 723 | 4140 / 5783 (71.6%) | 460 ms | 4273 ms | 6823 ms | 7074 ms | 86% | 144 MB |
| 1600 | 1132 | 8478 / 9056 (93.6%) | 1146 ms | 5070 ms | 6229 ms | 8394 ms | 85% | 189 MB |
| 3200 | 1396 | 10100 / 11168 (90.4%) | 2421 ms | 6420 ms | 8715 ms | 9766 ms | 74% | 167 MB |

Throughput tops out at **~2100-2450 requests/second, achieved already at 10
concurrent clients** - the single pinned core is at 82-93% busy from the very
first step, so more concurrency past that point buys queueing delay, not more
work done (classic single-server-queue behaviour). Latency degrades smoothly
and relatively gracefully through 200 concurrent clients (p99 already over a
second, but zero errors), then the **breaking point is between 200 and 400
concurrent clients**: at 400, throughput itself collapses (906 rps, down from
1788) and 39% of requests start failing outright. Past that it is
increasingly non-functional (70-94% error rates), though RPS and error rate
both bounce around rather than monotonically worsening - consistent with a
server that is thrashing against a fixed small resource (see §6) rather than
one that is falling over structurally.

**The server never crashed and never hung.** After the entire ramp (all nine
steps back to back, roughly 90 seconds of sustained overload including the
90%+ error-rate steps), a plain request answered `200` in 20 ms within
seconds of the last step ending, and `Get-Process` showed it still
`Responding`. Memory never ran away either - it moved between 98 MB and 360
MB across the run and settled back down, not a monotonic climb. So this
report's "breaking point" is a correctness/availability failure (wrong
answers - 500s and reset connections - under load), not a stability failure.
Pushed no further than 3200 concurrent clients: by that point the error rate
was already 90%+ and climbing concurrency further was adding client-side
noise (a few `:nxdomain`s appeared at 1600 and 3200, almost certainly this
Windows box's ephemeral-port/socket churn from opening thousands of outbound
connections per second, not a server symptom) without revealing new server
behaviour.

### Conditional requests (`If-None-Match`), same matched config

Real phones re-poll a page they already have, so every request here is a
`304` (or would be, absent overload):

| Concurrency | RPS | Errors | Median | p95 | p99 | Max |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 2027 | 0 / 16219 (0%) | 43.5 ms | 74.2 ms | 175 ms | 257 ms |
| 400 | 1600 | 2799 / 12799 (21.9%) | 180 ms | 860 ms | 1411 ms | 2293 ms |
| 800 | 1830 | 3294 / 14641 (22.5%) | 344 ms | 1104 ms | 2867 ms | 3246 ms |
| 1600 | 1850 | 7691 / 14803 (52.0%) | 859 ms | 2205 ms | 3554 ms | 3888 ms |

The important, slightly counter-intuitive result: **conditional requests do
not dodge the breaking point.** They fail in the same shape, at the same
concurrency, with the same error (§5) as full page requests, and are not
dramatically faster at c100 (2027 rps vs. 2142 for the equivalent fresh step)
despite a `304` never touching the renderer or the page cache. That is
exactly what you'd expect if the shared cost on both paths - not rendering,
not the page cache - is the actual bottleneck.

### The mismatched configuration, for comparison (default 16 schedulers, still pinned to 1 core)

Two spot checks, same workload:

| Concurrency | Config | RPS | p95 | p99 | Max |
|---:|---|---:|---:|---:|---:|
| 10 | matched (`+S 1:1`) | 2446 | 6.3 ms | 19.1 ms | 166 ms |
| 10 | mismatched (default 16) | 1591 | 20.4 ms | 42.0 ms | 413 ms |
| 200 | matched (`+S 1:1`) | 1788 | 139 ms | 1219 ms | 1713 ms |
| 200 | mismatched (default 16) | 1377 | 346 ms | 1125 ms | 1412 ms |

Leaving 16 schedulers running on top of a single pinned core costs roughly
**25-35% of throughput** and noticeably worse p95 tail latency at both
concurrency levels tested, from scheduler contention alone - real money left
on the table for a one-line startup flag, though not the catastrophic
failure an earlier, contaminated run of this same comparison first
suggested (that earlier result turned out to be the IPv6 client bug in §3,
not a scheduler effect - corrected here rather than left in).

## 5. First bottleneck, with evidence

**`OpenResults.Repo`'s Ecto/DBConnection pool - `pool_size: 5`, the
production default - run out under load, because every single request, hit
or miss, does one real query through it.**

`OpenResultsWeb.Plugs.Revalidate.call/2` runs ahead of the router on every
read route and, before it ever consults the page cache, calls
`OpenResults.Snapshots.latest_id/1` - a real `SELECT ... FROM snapshots ...
LIMIT 1` through `OpenResults.Repo`. That is a deliberately cheap,
index-backed lookup (the module's own docs call it "a primary-key lookup"),
but *cheap* is not *free*, and it is never skipped: it runs identically
whether the request ends in a fresh render, a page-cache hit, or a bare
`304`. §4's conditional-mode numbers are the direct proof - a pure-`304`
workload breaks at the same concurrency, in the same way, as full requests.

The server log makes the failure mode explicit - 690 occurrences during the
fresh-mode ramp and 522 during the conditional-mode ramp, all of the same
shape:

```
[error] ** (DBConnection.ConnectionError) [Elixir.OpenResults.Repo] connection
not available and request was dropped from queue after 102ms. This means
requests are coming in and your connection pool cannot serve them fast
enough. You can address this by:

  1. Ensuring your database is available and that you can connect to it
  2. Tracking down slow queries and making sure they are running fast enough
  3. Increasing the pool_size (although this increases resource consumption)
  4. Allowing requests to wait longer by increasing :queue_target and :queue_interval
```

with queue wait times climbing as high as 2.7 seconds at the worst-hit
concurrency levels before DBConnection gives up on them. Those dropped
requests are what the client sees as `{:ok, 500}` and (once the connection
itself gets torn down under the pile-up) `%Mint.TransportError{reason:
:closed}` - which is the whole of the error mix in §4's tables; there is no
second, independent failure mode in evidence anywhere in this test.

Rendering and the page cache are demonstrably **not** the bottleneck: the
render-skipping `304` path fails identically, and a 5-connection pool
exhausting itself well under 500 concurrent clients on a workload that is
otherwise mostly page-cache hits is a small, fixed number saturating - not a
CPU cost scaling up with page size.

## 6. Cheapest fixes worth making, in order

1. **Stop `Revalidate` hitting the database at all for the common case.**
   `Snapshots.latest_id/1` only ever changes on a publish. Caching it
   per-slug (an ETS table keyed by slug, exactly like `Snapshots`' own
   snapshot-body cache and `Revalidate.Page` already do, invalidated the
   moment `Snapshots.store/3` writes a new row) removes the database from the
   hot path entirely for every read that isn't a fresh publish. This is the
   fix that actually targets the bottleneck found in §5, and since §4 shows
   the DB pool is what breaks - not rendering, not the page cache - this
   should push the breaking point from ~200-400 concurrent clients up by
   roughly the same multiple the page cache already gives full renders (the
   `Revalidate` module's own docs cite 566x for that comparison). Zero
   database round-trips on the revalidation path, on a 2 vCPU box, is a much
   bigger win than anything below.

2. **Raise `POOL_SIZE`.** It is already an environment variable
   (`config/runtime.exs`), so this is a deploy-time change with no code
   touched at all. It will not fix the root cause - the pool is being spent
   on a query that fix #1 would make unnecessary - but going from 5 to, say,
   20-30 connections directly raises the concurrency level at which the pool
   starts dropping requests, which is worth doing today while #1 is still
   only a recommendation. Cheapest possible fix, smallest win of the three.

3. **Match BEAM's scheduler count to the box's actual core count** (`+S
   N:N`, N = the real vCPU count - `2` in production, not the `1` this test
   deliberately used). Measured directly in §4: leaving the default (schedulers
   = logical CPUs on the build/dev box, then constrained by cgroups/affinity
   in production) costs ~25-35% throughput and materially worse tail latency
   purely from scheduler contention, for the cost of one startup flag (or
   `os_mon`/`System.schedulers()`-driven `vm.args`). Free, immediate, and
   independent of fix #1.

Not recommended on this evidence: touching Bandit's acceptor pool or
timeouts, or the render path. Nothing in §5 points at either - the errors
are 100% attributable to the Ecto pool, and speculatively retuning a
subsystem with no observed fault in it risks hiding the real signal in a
future test.

## Cleanup

Every server and load-generator process started for this test was stopped
before writing this report: both server configurations (`+S 1:1` and
default-scheduler), the background CPU/memory sampler, and every
`mix run --no-start` load-generator invocation (each halts itself on
completion - see §3). A final process check showed no `erl.exe`/`beam`
process left running and port 4004 free (only OS `TIME_WAIT` entries from
already-closed connections, which are not a running process). The scratch
SQLite database, generated snapshot, and load-generator scripts remain under
the session scratchpad only; nothing besides this file was added to the
repository.
